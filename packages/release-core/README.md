# BESS ReleaseOS Intelligence Engine

TypeScript/Node.js document intelligence and human-approved submission release workflow. All code, fixtures, tests, and generated demo artifacts live in `packages/release-core/`. No frontend, database, external AI call, or shared configuration is included.

## Run it

Requires Node.js 22+ and npm. From this package directory:

```sh
npm ci
npm test
npm run typecheck
npm run demo
```

From the repository root, use `npm --prefix packages/release-core <command>` instead. `npm test` builds TypeScript and runs both the new workflow tests and the earlier engine's regression tests.

`npm run demo` executes real engine logic for a synthetic commercial battery project:

1. Ingest and explicitly approve engineering plan, battery specification, switchgear specification, and fire documentation V1.
2. Build Release 1 with four exact approved revisions.
3. Upload switchgear V2, changing its voltage rating from **480 V to 600 V**.
4. Extract exact source evidence, compare values, create an engineering review task, and block new package signoff. Earlier approved versions and Release 1 remain available.
5. Approve switchgear V2. The engineering task remains open.
6. Upload the updated engineering plan V2 and explicitly approve it while resolving the task.
7. Re-evaluate readiness, build Release 2, compare releases, and verify Release 1 is unchanged.
8. Generate both downloadable ZIPs and manifests.

Artifacts appear in ignored `demo-output/`:

- `release-<id>.zip`: `manifest.json`, independently verifiable `snapshot.json`, and original document files.
- `<id>.manifest.json`: document manifest entries for each release.
- `frontend-example.json`: actual JSON responses for incoming revision, semantic changes, impacts, readiness before/after review, complete releases, and release difference. This is generated by the workflow, not a hardcoded success response.

The fixtures are visibly synthetic and are not construction documents or regulatory advice.

## Preferred API

```ts
import {
  ReleaseOS, IntelligenceError, compareVersions, compareReleases,
  extractFacts, extractWithAdapter, verifyReleaseSnapshot, createReleaseZip,
} from '@releaseos/release-core';
```

`ReleaseOS` is the preferred site/package service. The previous `ReleaseEngine` API is retained in `legacy.ts`; its documentation is [LEGACY.md](./LEGACY.md). Root types `DocumentVersion` and `Dependency` now describe the preferred API. The older types remain exported as `LegacyDocumentVersion` and `PinnedDependency`.

| Operation | Input | Output |
| --- | --- | --- |
| `registerSite` | `Site` | Frozen site |
| `registerReviewer` | `Reviewer` | Frozen reviewer |
| `registerTemplate` | `PackageTemplate` | Frozen stage-specific configuration |
| `addDependency` | `Dependency` | Frozen graph edge; both document identities must exist in the same site |
| `ingestDocument` | `IngestDocumentInput` | `{ duplicate, version, comparison, impacts }` |
| `compareVersions` | Two version IDs (method), or two `DocumentVersion` objects (standalone function) | `VersionComparison` with old/new values and evidence |
| `calculateImpacts` | Source version ID | Affected documents, impacted template IDs, and review tasks |
| `reviewDocument` | Version ID, reviewer ID, explicit decision, notes, optional task IDs | Decision record and re-evaluated package readiness |
| `evaluateReadiness` | Site ID, template ID | Selected approved versions, pending/rejected IDs, issues, signoff readiness, optimistic token |
| `buildRelease` | Site/template IDs, signoff reviewer, notes, readiness token | Immutable `ReleaseSnapshot` |
| `compareReleases` | Two release IDs (method), or two snapshots (standalone function) | Added/removed/updated documents and semantic changes |
| `downloadRelease` | Release ID | `{ fileName, mediaType, bytes: Uint8Array }` |

Read methods: `listDocuments(siteId)`, `getVersion(id)`, `getLatestVersion(documentId)`, `getLatestApprovedVersion(documentId)`, `getDocumentHistory(documentId)`, `getReviewTasks(siteId)`, `getReviewDecisions(versionId?)`, `listDependencies(siteId)`, `getRelease(id)`, `listReleases(siteId)`.

`IntelligenceError` includes `code`, `message`, and `details`; `PACKAGE_NOT_READY` details contain the readiness issues. Errors such as `IDENTITY_MISMATCH`, `STALE_VERSION`, `UNAUTHORIZED_REVIEWER`, `SOURCE_NOT_APPROVED`, and `READINESS_CONFLICT` are suitable for mapping to application responses.

## Integration with Kaushik's Next.js application

1. Build this package. In the Next.js app's own `package.json`, add a `file:` dependency whose relative path points to this directory. If npm workspaces are adopted, register the package there instead. These are frontend-owner configuration changes; this package does not edit them.
2. Import it in a server-only service module. Next.js handlers using it must use the **Node.js runtime**, since the package uses `node:crypto`, Buffer, and ZIP generation. Do not bundle the service into client components or the Edge runtime.
3. Keep one service instance per tenant/project or use the application's eventual persistent service. A new `ReleaseOS()` per request loses state. A module singleton supports a single-process hackathon demo only; serverless cold starts and multiple workers do not share memory.
4. Map existing site IDs, document families, supplier IDs, and component IDs into the model. Document IDs identify a stable logical document, not one upload; the engine generates a fresh version ID for each distinct upload. Use separate document IDs for separate components or suppliers.
5. Register authorized reviewers from server-side identity data. Resolve `uploadedBy`, `reviewerId`, roles, active status, and signoff identity from authenticated sessions/admin configuration. This is a trusted library, not an authentication boundary. The browser must not self-register as an engineer.
6. Configure package templates from Kaushik's stage checklists. Add jurisdiction requirements explicitly. Do not map every NFPA documentation category into every initial permit submission.
7. Render `version`/`comparison`/`impacts` after upload. Show **latest upload** and **latest approved** separately. Display `issues` and open `ReviewTask`s as blocking work. Dependency paths explain which document caused the task; the source uploader and reviewer records provide identity context.
8. Submit explicit review decisions. Approving a source revision does not clear dependent tasks. A reviewer must approve the dependent document with `resolvedTaskIds` after the exact current source revision is approved. The dependent may retain its original bytes when engineering review confirms no edit is needed, or be uploaded as a new revision as in the demo.
9. Fetch `evaluateReadiness` immediately before human signoff. Submit its token as `expectedReadinessToken`. Apply Kaushik's additional compliance gates on the server as well, then call `buildRelease`; stale state requires refresh and another signoff attempt.
10. For a ZIP download handler, call `downloadRelease(id)` and return its bytes with `Content-Type: application/zip` and a safely quoted `Content-Disposition: attachment; filename="..."`. Authorize site/release access before calling the service. JSON snapshots and manifests are directly serializable; ZIP bytes should be returned as binary, not JSON.

Minimal service usage (site/reviewer/template are drawn from the application's trusted configuration):

```ts
import { ReleaseOS } from '@releaseos/release-core';

const engine = new ReleaseOS();
engine.registerSite({ id: 'demo', name: 'Synthetic BESS', jurisdiction: 'SYNTHETIC' });
engine.registerReviewer({ id: 'reviewer', name: 'Synthetic Engineer', roles: ['engineer'], active: true });
engine.registerTemplate({
  id: 'permit', name: 'Illustrative permit', stage: 'initial-permit', packageType: 'permit',
  requirements: [{ id: 'switchgear', family: 'switchgear-specification', label: 'Switchgear specification', minimumCount: 1 }],
  jurisdictionRequirements: [], consistencyChecks: [],
});
const incoming = engine.ingestDocument({
  documentId: 'switchgear', siteId: 'demo', family: 'switchgear-specification',
  supplierId: 'synthetic-supplier', componentId: 'switchgear-1',
  title: 'Synthetic switchgear specification', revisionLabel: 'V1', uploadedBy: 'uploader',
  fileName: 'switchgear-v1.txt', mediaType: 'text/plain',
  content: 'Revision: V1\nVoltage rating: 480 V\nCurrent rating: 800 A',
});
engine.reviewDocument({
  versionId: incoming.version.id, reviewerId: 'reviewer', decision: 'approved',
  notes: 'Explicit synthetic engineering review.',
});
const readiness = engine.evaluateReadiness('demo', 'permit');
const release = engine.buildRelease({
  siteId: 'demo', templateId: 'permit', reviewerId: 'reviewer',
  signoffNotes: 'Explicit synthetic package signoff.', expectedReadinessToken: readiness.token,
});
const zip = engine.downloadRelease(release.id);
// Return zip.bytes from the authorized server download handler.
```

For the full four-document integration example, import `createDemo()` / `runDemo()` from `demo/scenario.mjs` or inspect its generated `frontend-example.json`. [fixtures/synthetic-project.json](./fixtures/synthetic-project.json) contains concrete JSON site, reviewer, template, and upload data.

## Model and workflow guarantees

- `models.ts` defines `Site`, `DocumentFamily`, `DocumentVersion`, `ExtractedFact`, `SourceEvidence`, `Requirement`, `ReviewDecision`, `Dependency`, `PackageTemplate`, and `ReleaseSnapshot`, plus typed operation results.
- Stable document identity includes site, family, supplier, and component. Changing these across versions is rejected. IDs are unique within a service instance; version numbers increase per document. Original bytes have a raw SHA-256 hash, upload timestamp, external revision label, and internal version ID.
- Byte-identical re-uploads within a document return the original version and do not overwrite approval or latest-upload position, even if an old version is re-uploaded. Input metadata does not mutate an existing identical upload. A new logical document requires its own document ID.
- Latest upload and latest eligible approved version are separate. A newer pending/rejected upload blocks new signoff while retaining the earlier approved selection. Approvals are explicit engineer records including identity, timestamp, notes, version ID, and content hash. Uploader self-review is disabled by default. `allowAuthorApproval` exists for explicitly configured demonstrations. One active engineer decision per version is sufficient in this API; the latest explicit decision controls status.
- Semantic extraction recognizes labelled battery capacity (kWh), power rating (kW), manufacturer, equipment model, inverter quantity, voltage (V), current (A), frequency (Hz), and revision labels. It uses exact labelled lines; it does not guess numbers or units. Comparisons report fact additions/removals as well as changed values. An absent fact remains unknown, not inferred unchanged engineering information.
- Evidence references exact UTF-16 offsets, excerpts, and one-based line numbers in extracted text. Confidence 1 means an exact deterministic parser match, not engineering correctness. A page may be supplied by a trusted structured parser; the text-only AI adapter rejects page claims it cannot substantiate.
- Structured facts require exact evidence offsets. Claims not independently supported by the deterministic parser remain `needs-verification` and block readiness, even when an adapter claims high confidence. Correction currently requires a distinct document revision with supported source text. `extractWithAdapter` is explicit and optional; the engine never calls it or any external service automatically. Do not pass sponsor/customer documents to external adapters without authorization.
- Dependencies are site-local directed edges from source to dependent with explanation and optional relevant-field filters. An empty filter tracks any byte/semantic change. Upstream sources are included in package readiness and release closure. Cycles block readiness. Changed sources create explainable downstream tasks, not legal noncompliance findings.
- New uploads supersede obsolete open tasks but carry their unresolved changed fields forward. Approving a second source revision and uploading a cosmetic third revision cannot erase outstanding engineering review.
- Requirements are stage-specific, count stable document identities, and may target a component. Applicable jurisdiction rules are a separate list. Illustrative `documentationCategories` include commissioning, operations/maintenance, emergency operations, and decommissioning; there is no built-in universal NFPA checklist or certification claim.
- Internal conflicting values and upload/source revision-label mismatches block readiness. Cross-document consistency checks are opt-in and grouped by component, so unrelated battery/PCS quantities are not compared accidentally. Missing semantic fields are not automatically a missing document; configure application-level field requirements when necessary.
- The readiness token covers site, template, latest versions, decisions, graph, tasks, and reviewer state. Release build rechecks it synchronously along with readiness. The token is an optimistic concurrency check, not an authorization credential.
- Releases freeze site/template configuration, exact approved version IDs and hashes, original bytes, build metadata, reviewer approvals, dependency graph, resolved review tasks, and signoff notes. Later uploads/decisions/configuration changes cannot alter earlier snapshots. Incoming and returned records are detached and deeply frozen.
- `verifyReleaseSnapshot` checks the canonical manifest/snapshot checksum, individual original-byte hashes, version selection, and presence of approval records. This is integrity checking, not a digital signature or tamper-proof durable storage. Anyone with write access can recalculate hashes. ZIP exports sanitize filenames and include exact original bytes plus full metadata; they do not execute document content.

## Implemented and remaining work

Implemented: all six requested core workflows, configurable stage/jurisdiction requirements, optional adapter interface, reproducible ZIP export, synthetic end-to-end demonstration, and automated regression tests.

Application/production work remains: durable storage and hydration, cross-process transactions, authenticated authorization, jurisdiction-reviewed checklist content, operational upload limits, PDF/OCR parsing, optional provider-specific AI adapters, digital signatures, and external authority submission. State currently lives only in memory. Large original files are retained as base64 in snapshots; apply application upload limits and move blobs to durable object storage for production scale. No separate production database or frontend was created.
